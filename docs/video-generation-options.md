## 一、先说结论

镜间的画面是「电影感影调」优先，因此视频生成要的是**低速度、高保真、可精确控镜**，
而不是「一秒出片」。可选两条路，建议都留：

| 用途 | 走哪条路 | 代表 | 单价 | 5 秒成本 |
|---|---|---|---|---|
| 高质量成片（对标可灵 3.0 / 即梦） | 标准模型 API（第三方模型直调） | `seedance2.0/图生视频`（即梦同源） | ¥0.6/秒 | ≈ ¥3.0 |

| 想改 ComfyUI 图、自己调参 | 自部署工作流（RH币按 GPU 秒计费） | MiniMax H3 FL2VA 开源版 / Wan2.2 / LTX2.3 | 0.2 币/秒（24G） | ≈ 36 币/3 分钟 |

一句话：**要「对标可灵和即梦」的效果，就用标准模型 API 里的 Kling 与 Seedance 两个系列**——
RunningHub 已经把这两家的官方模型接进来了，不需要自己搭工作流。

**记账口径（2026-09-23 起）**：本站对外统一用**积分**，不接支付。积分只是额度单位，
背后对应两种货源：自部署工作流的 **RH币**（按 GPU 秒）与第三方模型的 **￥**（按秒）。
因为第三方模型要求「企业共享 Key」，**默认路线走 RH币 的工作流**，积分与 RH币 同尺度换算；
成片档再按需开启第三方模型（见第七节）。

## 五、接进镜间（静态站）的方式

站点是 GitHub Pages 静态导出，**没有任何后端**，所以：

1. API Key 不能进前端。要么用 Cloudflare Workers / 阿里云函数 做一层薄代理（只做
   「收请求 → 调 RunningHub → 轮询 → 回 URL」，Key 只存在于函数环境变量），要么第一版
   干脆由你在本机跑，生成结果手动入库。
2. 接口是异步任务模型：`提交任务 → taskId → 轮询状态 → 取输出`。
3. 两类 Key 不能混用（官方文档明确）：
   - **会员消费 Key**：AI 应用 / ComfyUI 工作流 / 上传文件（`/task/openapi/ai-app/run`、`/task/openapi/create`）。
   - **企业共享 Key（Enterprise-Shared）**：标准模型 API（`/openapi/v2/...`）与 `/openapi/v2/media/upload/binary`。
     官方文档写的是：Model API 与 LLM API **仅支持企业共享 Key**。走 Kling/Seedance 直调就必须先有这个 Key。
4. 标准模型调用形如 `POST https://www.runninghub.cn/openapi/v2/<模型路径>`，body 里带 `apiKey`
   （不是 header），并**必须带 `Host: www.runninghub.cn`**，否则部分接口 403。任务类型建议 `ASYNC`。
   图片先传 `/openapi/v2/media/upload/binary` 拿 `download_url` 再作为入参。
   AI 应用/工作流则是 `POST /task/openapi/ai-app/run`（`webappId` + `nodeInfoList`）。
5. 工作流节点的图生视频入参：`firstImageUrl` / `lastImageUrl` / `duration` / `cfgScale` / `sound` /
   `multiPrompt`，可灵 3.0 还支持 `elementList`（最多 3 项）与 `multiShot` + `shotType` 自定义分镜。
6. 价格预估接口 `/openapi/v2/price-preview/...` 可以在用户点「生成」之前先报价（内部成本核算用）。

## 七、积分制（对外唯一的额度单位，不接支付）

### 单位与换算

- **1 积分 = 1 RH币**（站内积分直接镜像平台账单单位，用户看一眼账单就能对账）。
  Standard(24G) 每秒 0.2 RH币 → **1 秒 Standard = 0.2 积分**；Plus(48G) 每秒 0.4 RH币（×2）。
  换算只有一个动作：**积分 = 实际 GPU 秒 × 档位单价**。
  已实测锚点：704×544 / 81 帧的图生视频在 Standard 上跑 99 秒 = **20 RH币 = 20 积分**；
  同档 60–180 秒即 12–36 积分。注册赠 300 积分 ≈ 15 条试镜档。
- 第三方模型（走 ￥）按内部成本汇率折算，汇率是**参数不是常量**（¥0.05/积分起步，
  随 RH币 充值折扣与厂商调价改），写在配置里，不硬编码到前端。
  参考：seedance2.0 一条 5 秒 ≈ ¥3.0 → 约 60 积分；可灵 3.0-std ≈ ¥2.6 → 约 52 积分。

### 规则（第一版）

| 动作 | 消耗积分 | 说明 |
|---|---|---|
| 影调诊断 / 风格匹配 / 提示词生成 | **0** | 全在浏览器本地算，没有服务端成本 |
| 试镜档：自部署工作流 5 秒 720p | **实测 20**（预扣 40） | 按实际 GPU 秒结算，多退少不补（见第九节实测） |
| 成片档：第三方模型 5 秒 | 52–60 | 需先有企业共享 Key 才会开启 |

- 新用户注册赠送 **300 积分**（实测下够 15 条 5 秒试镜档），每日签到 +20。
- **预扣 → 结算 → 退还**：提交任务时预扣上限值，任务成功后按实际秒数结算，失败/超时**全额退还**。
  幂等键用 RunningHub 的 `taskId`，重试不重复扣。
- 流水表只追加、不修改（`credits_ledger`：user_id / delta / reason / task_id / created_at），
  余额由流水汇总得出，不做「余额字段自增」。
- **不接任何支付**：积分只来自赠送、签到、邀请码。将来若要卖，是加一条充值入口，不动上面这套。

### 静态站的现实

GitHub Pages 上没有服务端，纯前端的额度存在 `localStorage`，清缓存即归零——**只能当体验用，
不能当准数**。要真做准，需要一个薄代理（Cloudflare Workers + KV/D1，只做「发任务 / 查任务 /
扣积分」三件事，Key 只存在环境变量里）。第一版建议：前端展示额度 + 服务端按 IP 限流，
把「严格账本」放到代理上线之后。

## 八、积分路线的最终选型（2026-09-23）

模型不是猜的：走 `POST /api/portal/workflow/detail`（body `{"workflowId": …}`）拿到了每条工作流

### 主力：Wan 2.2 I2V-A14B（fp8）+ LightX2V 蒸馏 LoRA

镜像站上跑的确实是同一套权重：

```
Wan2_2-I2V-A14B-HIGH_fp8_e4m3fn_scaled_KJ.safetensors
Wan2_2-I2V-A14B-LOW_fp8_e4m3fn_scaled_KJ.safetensors
Wan21_I2V_14B_lightx2v_cfg_step_distill_lora_rank64.safetensors
umt5-xxl-enc-bf16.safetensors / Wan2_1_VAE_bf16.safetensors
```

## 九、真实运行：一条 5 秒 = 20 积分（2026-09-23 实测）

用站内画面 `teahouse-window-1672.webp` 作首帧，在推荐工作流的 AI 应用页
（`/ai-detail/1949884135491985409`）提交了一条真实运行，参数全默认（704×544、81 帧、6 步、Standard）：

| 来源 | 数字 |
|---|---|
| **实际账单**（任务 `2102708158807113730`） | **成功 · 01:39（99 秒）· 20 RH币** |
| 应用页自报「预计消耗」 | ≈ 89 RH币（`/api/cost/average` 的 `avgCoin`） |
| 提交时的预扣接口 `/api/user/task/work/valid` | `coinNum 65` · `duration 312` 秒 |
| 产出 | 704×544 · 5.06 秒 · 1.2 MB mp4 |

结论：

- **一条 5 秒试镜档 = 20 积分**（0.2 币/秒 × 99 秒真实 GPU 时间）。平台自己的两个预估值
  （89 与 65 币）偏高 3–4.5 倍，**唯一可信的数字来源是账单页**（`/call-api/bill-task`）。
- 预扣上限已从 180 改为 **40**（实测的两倍），结算后照旧退还差额。
- 300 积分的注册赠送现在够跑 **15 条**试镜档；按 180 预扣时只够 1 条多。
- 计费模型另有两条佐证：账号里一个 3D 任务 3 分 49 秒（229 秒）扣 92 RH币 → **0.40 币/秒**
  （即 Plus 48G 档，与 0.2/0.4 的档位表一致）；一条**失败**的文生图扣 **0 RH币**——失败不计费，
  与代理「失败全额退还」的设计一致。
- `/api/system/getConfig` 里 `loginDailyCoin = 100`：每天登录送 100 RH币（当前余额 1,008 币）。

## 十、主力工作流的节点结构（下载 JSON 实测）

从工作流页的「下载」拿到原始图（25 个节点），存在 `.studio/workflows/wan22-lightx2v-6step.json`

结构是标准的 **Wan 2.2 双阶段（high/low noise）i2v**：

把帧数提到 121 或分辨率提到 1280×704 之前，先跑一条看账单。

## 十一、文生视频（t2v）的真实价位：84 积分一条

**那张 i2v 工作流不能做纯文生视频**——它的 `LoadImage`（节点 4）→ `WanImageToVideo`（节点 5）
是硬接首帧的，没有首帧就没有画面。文生视频要用同族的 T2V 图。

实跑（提示词「一只橘白色小猫从米白色沙发上跳下来…」）：

| 工作流 | 档位 | 参数 | 实际账单 |
|---|---|---|---|
| (KJ版)Wan2.2 文生视频精准调度加速版V4 `1950086984476835841` | Standard | 1024×768 / 81 帧 | **成功 · 06:57（417 秒）· 84 RH币** |
| Wan2.2 14B+LightX2V 6 步图生视频（对比） | Standard | 704×544 / 81 帧 | 成功 · 01:39（99 秒）· 20 RH币 |

同样 5 秒，**t2v 是 i2v 的 4.2 倍**（84 vs 20）。两个原因：像素数是 2.1 倍（1024×768 vs 704×544），
而且 t2v 那条图没有 i2v 那套把采样压到 6 步的调度。产出规格：1024×768 · 5.06 秒 · 1 MB mp4。

⚠️ **同一族模型有个 20 倍的坑**：Aquila 的「Wan2.2-14B 文生视频」应用页报价
**≈401 RH币**，而且是 **Plus（48G）**档。同一个 Wan2.2 T2V-A14B，只是没加速。选型时先看
应用页的「预估」和档位标签，再决定点不点。

对镜间的含义：站点的主线是「用户上传一帧 → 出片」，属于 i2v（20 积分）；文生视频更适合做
「无素材也能试试」的引流档，价格要单独定，不能和 i2v 一个价。

## 十二、五类效果的实测矩阵（含抽帧验证的帧率）

全部用站内画面做首帧/首尾帧，Hermes 本地抽帧（ffmpeg 全帧抽出 + 逐帧差异）核对，不靠观感：

| # | 效果类型 | 工作流 | 分辨率 | **帧率** | 时长 | 帧数 | 重复帧 | RH币 |
|---|---|---|---|---|---|---|---|---|
| 01 | 图生视频（蒸馏 6 步） | Wan2.2 + LightX2V | 704×544 | 16.0 | 5.06s | 81 | 0% | 20 |
| 02 | 文生视频（KJ 加速 V4） | Wan2.2 T2V | 1024×768 | 16.0 | 5.06s | 81 | 0% | 84 |
| 03 | 首尾帧过渡（**原生 24fps**） | LTX2.3 首中尾帧 | 1536×832 | **24.0** | **10.06s** | 241 | 0% | 39 |
| 04 | 首尾帧（名字带 smooth） | WAN2.2 smooth + rife49 | 720×1280 | 16.0 | 5.06s | 81 | 0% | 37 |
| 05 | **补帧 ×2 + 高清放大** | 视频高清放大2倍补帧 | **1408×1088** | **32.0** | 5.03s | 161 | 0% | 38 |
| 06 | 原生 24fps 直出 | 万相2.1 直出 1080P24帧 | — | — | — | — | — | **失败 0** |
| 07 | 文生视频 · 竖版运镜 | 文生视频｜高清流畅 wan2.2 | 720×1280 | 待核 | — | — | — | 115 |

### 三条结论

1. **Wan 系（含 t2v、含名字里写 smooth 的首尾帧）输出一律 16.0 fps**，且零重复帧——
   是真 16fps 内容，不是编码注水。**工作流名字里的"流畅/smooth"不能作为帧率依据**，
   04 那条权重里明明有 `rife49.pth`，成片仍是 16fps，必须抽帧验证。
2. **原生高帧率只有 LTX-2.3 成立**：24.0 fps · 1536×832 · **10 秒** · 39 币。
   按「币/帧」算它最便宜（0.16），Wan 6 步 0.25、t2v 1.04。
3. **把已有 16fps 素材救成平滑，补帧 ×2 那条已验证**：704×544/16fps → **1408×1088/32.0fps**，
   161 帧零重复，逐帧平均差异从 2.05 降到 1.14（插入的是真插值帧），38 币 / 3:09。

### 推荐的组合（给站点用）

- 用户传一帧 → `Wan2.2 6 步`（20 币）拿初稿；若要成片顺滑 → 再进 `视频高清放大2倍补帧`（38 币）
  → 32fps 高清成片，**合计 58 币**。
- 想要"原生 24fps + 更长"的展示片/片头：直接 `LTX2.3 首中尾帧`（39 币 / 10 秒），
  它比 Wan 系一帧还便宜，且自带音频 VAE（产出文件名带 audio）。
- 「万相2.1 直出 1080P24帧」那条实测**失败**（0 币，失败不计费），不要写进选型。

### 运营坑

- 应用页的「立即运行」要等云实例握手（约 30 秒）后才生效；**上传视频后还要再等 30–35 秒**
  让上传落地，否则点了无反应也不报错。
- 同一个 Camoufox profile 副本不能被两个脚本同时打开（会抢锁直接启动失败）——浏览器任务要串行。
- **抓产出链接要按任务号核对，别用「页面上新出现的 mp4」**：应用页自带示例片，很容易误当产出。
  可靠办法是点开「我的生成」，读 `/api/output/v2/history`，用 `promptResponse.prompt_id` 对上任务号。

## 十四、清晰度 / 平滑度的调参线路（可上线的两段式链路）

站点要的是「上传一帧 → 出清晰且平滑的成片」，而 H3 图生视频应用是**固定 832×448 / 24fps**，
分辨率与帧率都不在应用表单里，所以第一段定 H3、第二段做放大+插帧：

| 段 | 应用 | 关键参数 | 实测产出 | 真实扣费 |
|---|---|---|---|---|
| ① 生成 | `MiniMax H3 FL2VA开源版-图生视频` `2102682373744848898` | 图 + 提示词（分辨率固定） | 832×448 · 24fps · 带音频 · 5.2s | **58 币 / 2:23** |
| ② 放大+插帧 | `视频高清放大补帧V2.0` `1903013826319519745`（**Standard 档**） | 输出分辨率=1（2×）· 是否插帧=开 · 倍率=2 | **1664×896 · 48fps · 带音频** · 0% 真重复帧 | **55 币 / 4:35** |

**一条 5 秒成片的完整成本 ≈ 113 币（58 + 55）**，两次 API 调用。

### 第二段的三种配置（同一段 08 号原片）

| 实验 | 配置 | 产出 | 扣费 |
|---|---|---|---|
| X | 只放大（分辨率=1，插帧关） | 1664×896 · 24fps | 55 币 |
| Y | 只插帧（分辨率=0，倍率=2） | 832×448 · 48fps | **39 币** |
| 09 | 放大+插帧（默认） | 1664×896 · **48fps** | 55 币 |

### 测量的坑（重要）

判断「有没有真插帧」必须用**严格阈值**（逐帧平均差异 < 0.05 且极值 ≤ 2）。用 0.5 这种松阈值，
会把**插帧正确**的低运动画面误判成「27%~41% 重复帧」——因为 24fps 补到 48fps 时，逐帧差异本来就会
减半（实测 1.137 → 0.560）。正确做法是同时看两件事：帧率翻倍 + 逐帧差异减半 = 真插值；
帧率翻倍但差异不变 = 只是复制帧。

### 编辑器侧的旋钮（图 JSON 实测）

H3 的图里可调的节点（`下载` 拿 JSON，存在 `.studio/workflows/h3-fl2va-i2v.json`）：

| 节点 | 作用 | 字段 | 默认 |
|---|---|---|---|
| `RHMiniMaxH3FL2VATarget` | 画面尺寸与时长 | `aspect_ratio` / `duration_seconds` / `width` / `height` | auto / 5 / 832 / 480 |
| `ImageResize+` ×2 | 实际缩放目标 | `width` / `height` | 832 / 832 |
| `CreateVideo` | 交付帧率 | `fps` / `bit_depth` | 24 / 8 |
| `RHMiniMaxH3DualSigmaSampler` | 质量与速度 | `sigma_points` / `velocity_stride` / `accel` / `cache_dit_*` / `sampler_mode` | 50 / 4 / manual-velocity / 0.12·2·4 / euler |

编辑器接口形状（抓包）：`/api/workflow/copy` {workflowId, copyMode} → 实例 id；
`/api/workflow/getContent` {workflowId, contentType:"0"} → 图；`/api/instance/access/auth` 握手
（在握手完成前点「运行」不会排队，也不报错）。
